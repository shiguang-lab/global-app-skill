# 业务结果报告格式示例

本例提炼自用户指定的 `analysis/借款流程分析.html`：按 App 分组、按业务阶段连续阅读，流程图与对应原始 UI 就近查阅。只复用阅读结构，不沿用示例产品的状态值、条件、流程或供应商结论。

- [双 App 可视结构示例](report.html)：可离线打开的 HTML，含两个独立 App 章节、各自已渲染的流程图、阶段说明、折叠页面详情和字段表。
- [示例图源码](main-flow.mmd)：用于后续编辑，不展示在业务报告正文。

## 面向读者的内容

报告回答：功能做什么、入口在哪里、何时显示、用户做什么、成功/失败/取消后去哪里。只呈现分析结果、业务规则及原始页面，不要求读者阅读代码来理解结论。

代码、接口、哈希和运行日志用于内部分析及复核。默认不在正文、折叠面板、附录或导航中放“证据”“原始请求”“代码核对”等入口；不要只是用 CSS 隐藏仍被写入报告的材料。用户明确要求技术细节时再单独提供。

## 结论表达规范

**先回答业务问题，再解释条件与过程。** 总览、App 概述、阶段摘要和对照表单元格的第一句都要有明确的业务判断，读者不必自行从页面描述中推导结论。使用“谁／在哪个环节 + 在什么条件下 + 执行什么动作／产生什么结果”；条件较长时，先写简短结论，再单列触发条件和操作后去向。

- 问“是否弹出授权”，先回答“自动弹出／点击后进入／条件触发”等已验证行为，再列条件；不能用“保持某首页”“展示某卡片”等邻近现象代替回答。未直接观测授权是否出现时继续补证，不能由页面未跳转推断没有弹窗。
- 问“何时出现”，写清用户所处页面、实际触发事件和必要条件；问“完成后怎样”，写明完成的是哪一动作、进入哪个页面或继续哪项业务。标题也应表达关键判断，例如“验证码验证通过后继续资料提交”，不使用“相关处理”“其他说明”等空泛名称。
- 每句话只承载一个判断。优先使用“显示、打开、提交、返回、保留、禁用、重试”等动作；避免“支持相关能力、进行相应处理、完成后恢复、场景下可展示”等缺少对象和结果的表述。
- 正文保留已核实且与问题有关的结果。省略“不支持某功能”“未提供某页面”等对不存在内容的罗列。实际存在的拒绝、失败、取消和重试分支，直接写用户操作和结果，例如“拒绝相机权限后停留在资料页”。
- “按配置、满足条件、沿用相同条件、由调度决定”不能作为结论终点。展开已核实的关键条件，或链接本 App 内已经完整列出的同一规则；不能让读者寻找隐含前提。技术字段翻译成业务含义，例如“授权弹窗配置已下发、按钮文字非空”，而非裸列内部类型码。
- “可”表示能力，“会”表示条件满足后的实际行为，“必须”表示不能绕过的门槛，三者不能互换。一次受控运行不证明所有用户默认如此，客户端具备入口不证明生产环境一定启用。
- 专业性来自对象、条件、动作和结果准确，不来自术语密度。“额度卡片场景”应明确为“首页显示可借额度卡片时”；只有卡片数据的证据，不得改写成“真实授信通过后”。“回前台”按实际操作写成“重新打开 App”或“返回首页”，不能混用。

### 对照表必须比较同一问题

每行只比较一个业务判断，列出的 App 在同一行回答相同问题、使用同一粒度。必要时拆成“触发方式、触发条件、用户操作、操作后去向”几行，不能一列写入口条件、另一列写刷新后的页面，也不能把“授权范围”和“授权完成后的客户端去向”放在同一行。

征信类分析尤其要分开：**展示授权入口、用户同意授权、提交授权结果、实际发起征信查询**。协议允许定期查询是授权范围；页面出现或授权成功不是查询已执行。其他业务同样区分入口、确认、提交与最终执行，不为让结论醒目而升级事实。

下列只是表达示例，前提是相应条件和结果已被核实，不代表任何示例 App 的新结论：

| 不合格表述 | 改写方式 |
|---|---|
| 额度卡片场景可展示提示，需满足调度与内容条件 | **首页条件触发授权弹窗。** 触发条件：请求间隔已满足、首页没有其他弹窗，且收到的授权弹窗配置包含非空按钮文字。适用页面：首页显示可借额度卡片时。 |
| 相同首页条件下，回前台与刷新均保持首页 | 若已直接核对授权行为，写“**返回首页和刷新首页均不触发征信授权。** 条件：没有征信授权待办，也没有首页授权引导。”；若只观察到页面未跳转，不能作出该判断，须补看弹窗和授权入口。 |
| 完成后恢复资料提交 | **授权成功后继续提交银行资料。** 不把“完成”留给读者猜测。 |
| 默认声明允许后续定期查询 | **授权范围包含后续定期征信查询。** 这是授权内容，单列授权期限及适用期间；不据此写成“系统会定期查询征信”。 |

总览先用一至两句给出各 App 的核心判断和最重要差异，再放同维度对照表；每格采用“**明确判断。** 关键条件／后续”结构，复杂条件移入对应 App 的阶段说明并提供定位链接。不要把整段实现过程塞进单元格，也不要通过删掉必要条件获得表面简洁。

## 必需的总分结构

除非用户明确指定其他结构，先按下列层级组织大纲，再填入已审定的业务结论。标题措辞和阶段数量按实际功能调整，层级与归属必须保留；“沿用现有格式”不允许覆盖本结构。

```text
报告标题：App 名称 + 本次分析主题
业务总览
  直接回答核心问题
  各 App 的核心结论、关键差异与阅读入口
App A · 本次主题
  本 App 的业务概述、阶段导航与完整主流程图
  阶段 1
    条件 → 用户操作 → 结果与后续
    相关分支、字段/权限、阶段子图
    本阶段页面/状态说明与对应原始 UI
  阶段 2……
App B · 本次主题
  本 App 的业务概述、阶段导航与完整主流程图
  阶段 1……（同上，独立讲完本 App）
```

总览只做结论概括和差异比较，详细条件、办理规则、流程图和 UI 回到各自 App 内。单 App 保留“总览 → 该 App → 阶段/页面”层级；专项分析仍按 App 组织，只展开专项及必要上下游。

HTML 沿用示例的 `.reading-map`（总览）、`.product-document`（App）、`.business-stage`（阶段）、`.stage-pages`/`.screen-detail`（页面详情）组织嵌套；每个 App 的二级标题直接包含 App 名称，不能只在小标签中写名称。Markdown 对应二级标题为总览/各 App，三级标题为阶段，四级标题为分支或页面。锚点带 App 前缀，避免多 App 同名阶段互相串联。

后续补查、Mock 或新增截图必须合并到所属 App 的对应阶段：把观测转成条件和行为结论，把图片放到该阶段页面详情。不得在 App 章节之外追加“新增 Mock 验证”“补查过程”“运行结果”等同级章节，也不得保留安装/注入方法、测试用例通过表或待确认清单。它们属于内部记录；报告只保留理解业务所需的已知条件与图片来源。

## 按层级填写内容

### 1. 标题与业务总览

- 标题写 App 名称和本次分析主题；仅保留必要日期、App 版本。
- 用一段话直接回答核心问题，再用少量结果卡片概括关键区别。
- 提供可点击的主线阶段导航。
- 多款 App 时提供按 App 选择的阅读入口，必要时折叠展示差异对照；全局导航以总览和 App 为主，阶段导航位于各自 App 内。
- 不以取包渠道、反编译方法、设备恢复或验证范围清单开篇。

### 2. 按 App 独立组织完整链路

每款 App 连续讲完本次范围内的流程，避免跨 App 按“所有登录页”“所有资料页”混排。仅分析一个 App 时保留一个产品章节；指定功能仅保留该功能与必要上下游，不为套模板扩展还款、复借等无关环节。

产品章节包含：

1. 一段业务概述。
2. 主线阶段导航。
3. 可展开的完整流程图；复杂场景另有对应阶段子图。
4. 按顺序展开的业务阶段。

流程图用 Mermaid 实际渲染。节点、箭头写业务动作和条件，点击节点可展开对应说明或原始 UI。保留适合宽度/原尺寸阅读；图源码保存在内部分析目录。

### 3. 每阶段先讲业务，再展开页面

```text
阶段编号 · 阶段名称
核心结论：一句话直接说明本阶段何时发生、关键动作与结果。

进入条件：用户处于什么状态，从哪里进入。
用户操作：填写、选择、确认或等待什么。
成功后：转到哪一步，改变什么业务状态。
失败或其他条件：失败、取消、权限拒绝、配置变体如何处理。

[可展开] 本阶段具体分支：标题 + 条件 + 操作 + 后续
[可展开] 本阶段流程图
[可展开] 字段、权限和办理规则
[可展开] 本阶段页面与原始 UI（按页面/状态分组）

下一阶段 / 返回业务总览
```

所有用户状态先翻译成业务含义，例如“授信审核中”“授信通过、未借款”。不要用内部数值、字段名或路由作为主要解释。

入口显示条件要结合用户状态、页面选择及按钮含义解释。首页显示某入口，与独立页面打开方法是否再次校验资格，是不同层次；不能用后者替代 UI 显示分析。

### 4. 原始页面的统一说明

```text
页面编号 · 页面/状态名称
当前状态或进入条件（摘要）

原始完整截图（可展开/查看原尺寸）
如何进入：上一个入口/页面/用户动作。
何时显示：对应状态和必要条件。
界面显示：核心内容、输入和默认选项。
用户操作：按钮、选择、确认、关闭。
操作与后续：成功、失败、取消、重试或续办的去向。

字段/权限表：数据或字段 | 要求 | 交互、条件与校验
返回对应流程图 / 上一步 / 下一步
```

页面编号用于导航原图，不是证据编号。没有截图的状态只讲已知业务，不编造界面、按钮文案，也不用重绘图冒充 App。

截图旁用“原版 App 界面”或“原始 H5 页面 · 演示数据”等简短说明即可。不得把演示金额、身份资料、模拟审批或 SDK 回调当作真实报价、真实审核通过或到账。

### 5. 分支与业务规则

- 关键判断放在发生的阶段旁，不全部挤到末尾。
- 场景对照表可用“场景 | 出现条件 | 用户操作 | 处理与后续 | 对应 UI”。
- 字段表可用“数据/字段 | 必填/可选/条件必填 | 交互、联动与校验”。
- 各种配置是替代路径，不排成所有用户都必经的连续步骤。
- 业务规则不清楚时先回到代码、App 交互与隔离 Mock 补证，按 [调研闭环与完成条件](../../references/completion.md) 关闭问题；最终正文写确定的条件、操作和结果。确认不存在的功能不列；真实阻塞只在内部记录和聊天中说明，报告不出现“待确认/未完成/受限”等状态，也不能因此停止范围内走查。

### 6. 专项内容与收尾

供应商、权限比较等仅在用户要求或本次主题需要时加入：

- 供应商表：业务类别 | 供应商/服务 | 用途与适用范围。
- 仅列已核实的技术服务、资金/征信机构和支付渠道；不加代码路径、SDK 包名、行号或哈希。
- 页面示例来源与已验证的适用条件在相应位置简短说明；末尾无需附内部取证包或环境恢复记录。

## 呈现约定

- 深色标题区、浅色底、白色业务分区；业务总览和 App/阶段导航容易找到。
- 默认显示主线解释、业务结论与关键条件；分支、字段和原图按需展开，避免巨图或密集截图占据整页。
- 点流程图节点或页面链接时，自动展开其所在折叠层并滚动到目标；不是只改 URL 而页面仍折叠。
- 一图对应一处业务位置，避免单独图册与正文脱节；原尺寸查看不改原图。
- 内嵌必要图和图片后检查桌面、手机、断网阅读与锚点；不要依赖外部源码链接才能看懂结果。

## 结构检查

在[报告审查工作流](../../references/report-review-workflow.md)的 10.2 核对下表。以实际标题树或 DOM 章节树为准，核查 App、阶段和页面的归属与嵌套。

| 检查 | 通过条件 |
|---|---|
| 总分层级 | 总览在前，第 2 步确定的每款 App 各有一个独立的产品章节；App 名称出现在该章二级标题中，没有游离的 Mock/补查/过程章节 |
| App 内闭环 | 每款 App 章内都有本 App 的概述、阶段导航、主流程图及顺序排列的阶段 |
| 阶段与 UI 归属 | 各阶段含条件、操作与正常/异常去向；分支、字段/权限和原始 UI 嵌在所属 App/阶段内，截图不是独立研究日志或另一款 App 的附件 |
| 导航归属 | 总览指向各 App，App 内导航指向本 App 阶段，图节点和对应页面位于正确章节 |
