# 业务流程、功能入口、UI 与交付

仅用于业务调研分支；纯 UED 请求使用 [UED 工作流](ued-workflow.md)。页面发现、技术栈处理、动态 H5 路由范围和图片提取统一调用 [共用页面提取模块](ui-extraction.md)，本文件只定义业务走查和报告验收。

报告格式先参考 [业务结果报告格式示例](../examples/business-results-report/README.md) 和 [可视示例](../examples/business-results-report/report.html)。下面的取证、编号和复核要求属于内部分析工作，不等于要将这些材料展示给业务读者。

## 第 8 步：按业务问题走查

先建立用户可读主线和待验证分支，再用代码与运行证据填充，不能从截图文件列表反推一条假流程。按 [调研闭环与完成条件](completion.md) 在 App 原宿主执行必要场景，只有代码、浏览器演示或终态截图不能通过交互验收。

贷款类 App 的历史主线可作领域例子：登录 → KYC → 申请 → 审核/放款 → 账单/还款 → 结清 → 复借；其他 App 按其业务建立主线，不硬套贷款模板。指定功能调研只保留相关节点与必要上下游。

每个入口/页面/状态用稳定 ID，至少回答：

| 维度 | 需记录的事实 |
|---|---|
| 所属 | 哪款 App、业务阶段、功能与渲染宿主 |
| 入口 | 从哪页、哪个按钮/菜单/协议链接进入；或何接口/状态自动跳转 |
| 显示条件 | 用户状态、权限、字段取值、服务端状态、灰度开关、标签及条件组合 |
| 字段与交互 | 输入项、必填/条件必填、默认值、校验、展开/联动、协议勾选与提交门槛 |
| 权限与 SDK | 何时请求、拒绝/永久拒绝后怎样处理，业务依赖与 SDK 回调/错误 |
| 去向 | 主要操作、提交成功/失败、取消、返回、重试、退出后续办各去哪里 |
| 原始 UI | 完整页面/弹层截图、真实宿主与取证模式、源帧与哈希 |
| 证据 | 对应代码/配置/接口、实际操作日志、fixture 与未知项 |

业务条件与 fixture 分别存放。例如“订单放款异常且需要更换收款账户”是业务条件；模拟状态码/订单号是取证输入，不能替代用户可理解的条件说明。

### 必须区分的关系

- 连续步骤、同页弹窗、字段联动、配置变体、服务端状态和独立业务支线，不统一叫“下一步”。
- A/B/C 灰度分组及可叠加配置，不称作新旧 APK，也不推断所有分组都在生产启用。
- 有组件但未找到有效入口的页面，继续查调用、条件、动态配置与实际导航；有依据判定为保留页面才单独归类，仍未查清则是待补证项，不混入当前主线或据此结束。
- 登录后依据业务状态续办，不默认所有存量用户都重新 KYC/申请。检查登录前路由恢复、服务端 nextUrl/jumpUrl 与返回优先级。
- 协议查阅入口与接受同意动作分开；按钮/协议默认勾选、未勾选禁用、勾选后可继续都需观察。
- 授信审核、单笔借款审核、放款状态、付款返回和账单入账是不同状态；推荐其他产品成功不代表本 App 或对方审批成功。
- 空记录申请入口与结清后复借入口分开；换卡可能只针对当前订单，不应强制回到整个 KYC 分组。

字段/权限只写有依据的实际合同：Manifest 声明、运行时请求、实际读取/调用、上传以及平台审核申报是不同层。指定联系人填写不等于读取整个通讯录，未见弹窗不等于没有权限或申报。

## 完整相关逻辑与 Mermaid 流程图（必需）

业务/功能调研报告必须用 **Mermaid** 展示流程图。第 8 步完成逻辑建模与图源码，第 9 步复核完整性/正确性，第 10 步实际渲染并交付。纯下载任务无需业务流程图。

“完整”以本次调研范围为边界：整款 App 覆盖全部已识别自有功能及相关业务链路；指定功能覆盖该功能的全部已识别入口、相关分支及必要上下游，不扩展为所有无关功能。没有客户端/运行证据的后台实现保留为未知，不为凑闭环虚构步骤。

### 绘制要求

- 先给简洁总览，再按功能/阶段提供必要子流程图。总览可折叠细节，但子图与状态矩阵必须覆盖已识别的重要逻辑，不能只画一条成功主线。
- 图中覆盖：自然入口与自动入口、前置条件、配置/用户状态分流、输入校验/权限和协议门槛、成功/失败/异常、取消/返回、重试、保存进度与续办，以及真实终点或后续状态。
- 决策边明确写业务条件；存在的正反分支都分析。跳过已完成步骤、恢复登录前入口、服务端 nextUrl、轮询/等待、跨 App 跳转分别按实际语义表达，不画成必经步骤。
- 连续步骤、可选配置变体、弹层和状态变化保持区别；A/B/C 等分组画条件分支，不能误连成 A→B→C 的顺序。
- 节点 ID 稳定并对应状态/UI 索引，关键边在现有结构化记录中对应 `from / to / condition / evidence / verification` 含义；可沿用项目原字段，不另造一份漂移的事实表。
- 节点和关键连线在内部记录中能定位相关代码、接口/配置或操作日志；报告中的页面节点链接到对应业务说明或 UI，不链接源代码。方法和证明范围保留在内部复核记录。报告用简短的页面来源标签和已验证条件保持准确，不逐条展示取证状态；真实阻塞按闭环规则保留在内部记录并在聊天说明，不进入报告。
- 默认用 Mermaid flowchart 表达业务顺序/条件；状态切换复杂时可补 Mermaid stateDiagram，接口交互确有必要时补 sequenceDiagram。不要用技术交互图替代用户业务流程。

第 8 步结束时，依据同一状态/证据矩阵生成 Mermaid 源码及功能描述草稿，供第 9 步逐项复核。图的完整性检查集中在第 9 步执行，不用生成图时的自检替代交付前事实复核。

## 原始 UI 采集

按 [共用页面提取模块](ui-extraction.md) 发现并采集，调用其 [截图与长图操作](screenshot-workflow.md)。业务范围不取消动态 H5 的全部路由提取规则；扩展图片进入共用目录/补充图册，正文只就近展示当前业务相关 UI，不把保留路由或直接定位截图写成自然业务入口。

共用模块负责宿主真实性、单屏/完整长图、来源像素、顶部/底部及失败原帧保留的验收；业务分支另核对每张引用图片与原代码的条件/步骤一致，不能用单页终态代替完整链路证据。

## 第 9 步：流程图与功能描述的事实复核（必需）

审查对象是第 8 步形成的待交付草稿：全部相关 Mermaid 图、功能正文、字段/权限表、状态说明和关联 UI。重新打开相应原代码/资源及操作日志，按下表核实，不能仅比较报告自己的图与 JSON，也不能把 Mock 的预期结果当独立来源。

| 对象 | 必须复核的内容 |
|---|---|
| 每张流程图 | 对照范围/入口/状态矩阵核查覆盖；区分主线、配置变体、弹层、跨产品与保留页面；自然入口有证据 |
| 每条关键连线/分支 | 条件、按钮/触发方式、请求与响应、下一跳吻合原实现；正反条件、失败/超时、取消返回、重试、草稿续办、等待/退出语义完整 |
| 每项功能主张 | “在哪、何时显示、怎么操作、会产生什么结果”逐项有依据；必填/可选、默认值、字段联动、校验、权限/SDK、成功失败条件描述准确 |
| 结论措辞 | 没把“支持/代码存在/条件命中”写成“当前默认/所有用户/必然”；未把合成金额/时间当生产参数，未把客户端提示或 SDK 回调写成后台事实 |
| 图文与 UI | 同一版本/配置/用户条件，ID 与截图/代码引用一致；没有用同一静态截图证明不同路径，也没以单页终态证明自然进入链路 |
| 截图完整性 | 可滚动页面有完整长图、顶部/底部与实际滚动容器证据、来源像素校验；单屏保留原图；失败项有原因及全部原帧，未被计为已完成长图 |
| 证据身份 | 核对 APK、恢复 DEX、实际加载 JS 和本地快照版本/哈希；远端资源不同则保留并说明，不能混用结论 |
| 范围与未知项 | 用户问题是否逐项得到回答；分别统计代码确认、实际走通、本地场景、原始 UI 与未覆盖内容，后台征信/审批/到账等不越界推断 |

必要的正反例包括开关关闭/缺失、缺字段、权限拒绝、重复操作、退出再进等，依据本次功能选择有影响的场景；不强行穷举无关组合。

### 复核记录及通过条件

在项目已有复核记录中保留以下信息；没有现成文件时使用任务目录的 `review.md`，不另复制一份业务事实表：

- 受审范围、包/资源版本、草稿版本，以及每个功能主张/图 ID/关键边 ID。
- 实际查阅的证据文件/代码位置、相关运行/fixture/UI 记录及证明范围。
- 逐项结论：通过、待证实、需修正；发现的问题、修正落点、修正后的再次核对结果。
- 已回答与未回答的用户问题、剩余未知项，以及允许交付的结论范围。

整体结论分为：**通过**（范围内问题有确定回答，必要 App 交互全部通过且无已知错漏）、**继续补证/修正**（存在待证实、缺分支、矛盾或无据主张，返回第 5–8 步）、**阻塞未完成**（满足闭环规则的真实阻塞，记录证据与恢复输入）。结果报告只写已核实的具体结论，取证状态与阻塞留在内部/聊天；单纯删未知项、补免责声明或修正 Mermaid 语法不能关闭业务问题。

以上是业务事实结论；[共用模块](ui-extraction.md) 的页面提取结论单独记录。扩展 H5 缺图不抹掉已证实事实，事实通过也不关闭图片缺口。第 10 步须检查正式或获准阶段性交付的实际图片，不以任何一个维度代替整体完成；仍有本次目标所需的图片缺口就不能宣布整项完成。

## 第 10 步：业务报告与质量检查

正文优先按 App/用户链路组织：业务总览 → 按 App 分组 → 每款 App 的完整主流程 → 各业务阶段及分支 → 就近展开页面状态详情与原始 UI。每个状态说明进入条件、界面显示、用户操作及成功/失败去向。把字段、权限和页面细节放在对应阶段按需展开，避免与流程脱节的大图册。

默认不输出代码证据、接口请求体、文件路径/行号、哈希、证据编号、逐边复核表、设备恢复记录和调研过程，也不将其隐藏在折叠区、附录或仅用 CSS 隐藏。报告是结果说明，不是取证包。用户明确要求技术分析或来源追溯时，再按请求追加相应材料。

同一 App 从头到尾连续可读，跨产品推荐另作支线；专门功能的报告围绕该功能，不放不相关步骤和范围说明表。保留用户认可的术语（例如 KYC），不创造会误导产品含义的名称。

对外交付业务报告与对应原始 UI。内部保留结构化入口/状态/边清单、代码/资源索引、fixture/运行日志、事实复核记录及未知项，以支持准确分析和后续更新；不把内部材料自动并入对外报告。已有数据文件按项目格式维护，避免再建互相漂移的重复事实表。

图、正文、导航和原始 UI 保持同一事实。流程图主线先简后详，复杂图及页面细节按需展开；将接口字段、内部状态码和配置名称翻译成业务条件。页面标注“原版 App 界面”或“原始 H5 页面 · 演示数据”等简短来源即可；不把模拟审批写成真实审批，金额、日期和身份示例不当作真实产品报价。范围内未知项先按闭环规则继续验证，不直接放进最终正文。真实阻塞、页面/H5 范围缺口及长图缺口留在内部记录并在聊天说明，不放进结果报告，不能因正文省略这些项就停止补证或宣称全部完成。

### Mermaid 的报告呈现

- Markdown 报告使用 `mermaid` fenced block；HTML 报告使用 Mermaid 实际渲染后嵌入 SVG，不能仅留下源码文本或流程图占位图。
- 在内部分析目录保留可编辑的 Mermaid 源码；默认不在业务报告中展示源码。HTML 中嵌入已渲染 SVG，提供适合宽度/原尺寸阅读及节点到业务说明或 UI 的导航。
- 实际检查每张图均成功渲染、无语法/运行错误、文字完整，桌面和手机可读；复杂图提供分层展开或必要缩放，不让巨大总图成为唯一入口。
- 用户要求离线/单文件时，打包实际需要的渲染资源或已渲染的 SVG，并保留 Mermaid 源码；在空目录和断网条件下验证图能显示，不能依赖未打包的 CDN。
- Mermaid 渲染检查和业务逻辑复核分别记录。图可显示、节点/锚点可点，不代表相关逻辑已经完整正确。

### 最终交付门槛

第 10 步使用第 9 步审定的功能描述和 Mermaid 源码进行排版/渲染/打包，不在这一阶段未经复核地添加业务结论。最终文件生成后实际打开报告，逐项对照审定草稿：

- **事实一致性**：最终显示的图、功能正文、字段/权限表与适用条件均与复核记录一致；条件和限定语没有在排版/合并时丢失。更新复核记录，注明最终文件、版本及检查结果。
- **变更回流**：新增或改动功能含义、条件、顺序、边或结果时回第 9 步；只改 CSS/布局可在第 10 步重测呈现，无需重复无关运行测试。
- **禁止带错交付**：存在未证实、需修正或缺少必要 App 交互的项时，返回补证，不得宣布完成；只有闭环规则允许时才先提供已核实结果；报告不写“未完成/待确认/受限”，阻塞与恢复输入在聊天说明。

另外执行呈现/工程检查，与事实复核分开记录：

- 页面/状态/图 ID 唯一，所有本地文件和锚点存在，图片加载完成且非零尺寸，截图 SHA-256 与清单一致。
- 桌面与手机查看主流程、分支、图片与返回导航，没有横向溢出、不可读文字或 JS 错误。
- 图的连线、分支条件和报告文字一致；原始 UI 没有被重绘，字段/条件和图对应。
- 用户要单文件/离线分发时，内嵌实际依赖与附件，复制到空目录并断网打开测试。历史 96 MB 单文件只是本次结果，不是通用大小目标。
- 恢复原包、代理和调试连接有内部实际核对记录；对外简要说明已验证结论适用的版本/条件；真实阻塞按闭环规则另在聊天中说明，不写进结果报告。

报告呈现方式遵循用户要求；没有指定时在现有 workspace 延续原格式。不要为了生成报告擅自创建外部站点或向他人发送内容。
