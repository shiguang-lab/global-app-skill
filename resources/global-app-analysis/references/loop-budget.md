# 回路预算与用户确认

预算限制重复尝试和整轮返工。按已定范围首次处理不同的来源、页面、路由或场景，以及第 9 步正常首审和无缺口时的例行复审，沿清单推进，不占额度。用稳定 ID 去重；同一根因影响多个页面时合并为一个卡点。

| 回路 | 每批自主上限 | 计数口径 |
|---|---|---|
| 第 3–4 步搜索新取包来源 | 3 轮 | 按取包记录领取轮次，无新增候选也计一轮。校验失败、换设备 profile 或换目录沿用原记录。 |
| 同一技术卡点 | 首次失败定位不计，之后最多 2 次修正重试 | 每次按一个新证据或可区分的假设做修正并验证，开始时记一次。适用于已知取包路径纠错、设备/调试副本、代码/H5 资源恢复、Mock、重拍及长图拼接。同一根因换工具、页面或步骤仍累计。无新依据时提前停。脚本自身的传输、刷新和轮询上限照常执行。 |
| 第 9 步补证和重审，包括第 10 步退回的事实问题 | 3 轮返工 | 每次汇总一批缺口，启动修正并回 9.1，记一轮。第 5–8 步补证、子 agent 分工及第 10 步退回共用同一证据返工计数；一轮内可修多个缺口。 |
| 第 10 步报告或图册成品修改与重审 | 每份交付物 3 轮返工 | 同一版本发现的问题合并修改，从最早受影响的环节重审，启动时记一轮。换章节、改名、重新渲染或换审查者仍累计。回第 9 步补证计入证据返工；审定后重新生成并初检成品不额外计为成品返工。 |

“轮”按回路分别指搜索轮次、技术重试次数、证据返工轮和成品返工轮；“批”指用户确认后重新开放的一组额度。不要用一个回路的计数代替另一个。

| 你要做什么 | 用哪个回路 | 命令 | 超限信号 |
|---|---|---|---|
| 找新的取包来源 | 搜索批次 | `attempts.py search-round` | 脚本退出码 1 + 错误文本；按第 3 步询问用户是否续开 |
| 同一技术卡点换一个可区分假设 | 技术重试 | `check_delivery.py reserve --key technical:<卡点ID>` | 退出码 3，暂停该回路等用户 |
| 第 9 步补证、重审或第 10 步退回的事实问题 | 证据返工 | `reserve --key evidence:task` | 退出码 3 |
| 第 10 步报告/图册修改与重审 | 成品返工 | `reserve --key artifact:<交付物ID>` | 退出码 3 |

跨步骤、跨会话、换工具或审查者时沿用同一任务账本和稳定 ID。取包搜索继续用 `attempts.py search-round` 及 `resume-search`；其余回路使用同一任务目录内由 `check_delivery.py` 维护的 `task-checks.jsonl`。

## 两个账本，两个 init

任务目录确定后先执行校验账本的 `init`，已有账本会原样保留；`review.json` 可以在后续阶段再创建。取包账本在第 3 步单独创建，两者不是同一个文件。

```sh
mkdir -p "$TASK_DIR"

# 校验账本：额度、续批、审查轮次
python3 "$RESOURCE_ROOT/scripts/check_delivery.py" init "$TASK_DIR/review.json"

# 取包账本：来源去重、搜索轮次（第 3 步）
python3 "$RESOURCE_ROOT/scripts/attempts.py" init --ledger "$TASK_DIR/attempts.json" \
  --package com.example.app --version-policy latest-available
```

重试或返工前执行 `reserve`，成功取得 ID 后才运行对应操作。完成后及时执行 `finish`，提供本次新增且可独立保留的结果文件。操作中断也保留其实际结果；在补齐之前，该领取记录仍未结案。`finish --outcome unavailable` 只用于领取后操作确实无法执行、没有可验证结果的情况；它不能作为 blocker 的 attempted 证据。路径本身不可执行时，在 `issue.paths.<路径ID>` 写 `status: unavailable` 和前置条件证据，不要用 `finish` 代替。

```sh
CHECK="$RESOURCE_ROOT/scripts/check_delivery.py"
RECORD="$TASK_DIR/review.json"
python3 "$CHECK" reserve "$RECORD" --key technical:loan-submit --action '根据请求日志验证提交条件'
python3 "$CHECK" finish "$RECORD" --id ID --outcome failed --evidence runs/loan-submit-ID.log
python3 "$CHECK" resume "$RECORD" --key technical:loan-submit --evidence approvals/loan-submit-next-batch.md
```

技术卡点使用 `technical:<卡点ID>`，证据返工使用 `evidence:task`，成品返工使用 `artifact:<交付物ID>`。ID 只能使用字母、数字、下划线、点和连字符（含中文），不要用 `:` 或 `/`。同一动作同时消耗整轮和技术卡点额度时，在一次 `reserve` 传两个 `--key`，任一超限都不领取。一次证据返工可包含多个单独领取的技术重试，整轮的结果在完成回查时登记。阶段审查和交付会重放账本，核对额度、续批记录和结果证据。

## 达到上限后怎么继续

1. 完成已领取的本轮验证。仍需重试时先领取下一轮。搜索批次由 `attempts.py` 以退出码 1 拒绝；校验账本由 `reserve` 以退出码 3 拒绝并记录「等待用户决策」。看到退出码 3 立即暂停该回路及依赖它的交付。独立节点可继续；没有独立工作时保存检查点并等待回复。暂停期间停止该回路的工具调用、轮询和子 agent 派发。额度用完且当前轮已通过时照常推进。
2. 合并当前需要用户决定的问题。说明哪个回路已用多少轮、已验证的结果、仍缺的证据，以及下一批要尝试的具体方法。让用户选择继续一批、提供输入或调整范围、先看已核实部分、停止。没有新的可验证方法时，优先请求具体输入或方向。
3. 用户明确同意继续后，将本次答复和对应回路记录到新的证据文件，对**每个获准的回路**执行 `resume`。只重置获准回路的当前批次，保留历史和其他计数。下一动作同时受两个已耗尽额度约束时，在同一次确认中列明两个回路。用户补充的素材可直接核验；要继续已耗尽的重试仍须明确授权。
4. 每次新批次再次耗尽且仍有问题，重新暂停并询问；上一次继续的同意只覆盖一批。用户调整范围时更新原范围与受影响的验收项；用户要求先看结果时按[完成条件](completion.md#真实阻塞与结论边界)验收已核实部分。等待用户决策不会把缺口标记为完成。
