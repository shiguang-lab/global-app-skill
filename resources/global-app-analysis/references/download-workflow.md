# 下载顺序与用户介入

本文件是业务调研/UED 提取共用的前四步。只下载时按下面 `/4` 示例执行并结束；业务/UED 使用 `/10`，第 4 步后分别继续 [业务第 5–10 步](research-workflow.md) 或 [UED 工作流](ued-workflow.md)。所有下载渠道顺序、三轮搜索和去重约束保持一致。第 1/4 步的通过条件以[主工作流](guide.md#主工作流)的十步表为准，本文件只展开操作与降级。

## 主流程的状态与依赖

`环境检查 → 目标识别与信息补齐 → 获取安装包 → 校验归档`。渠道选择和依次尝试都是“获取安装包”的子流程；网络恢复与结论交付是所有退出路径的收尾动作。

状态为 `pending`（待执行）、`running`（进行中）、`waiting_user`（等待用户）、`succeeded`（完成）、`failed`（失败）、`skipped`（跳过）。这里是 skill 执行约定，不依赖外部工作流服务；agent 按此顺序调用现有工具。

- 第 1 步是硬门槛：无可用 Android 设备或完整 AVD 时立即 failed，中断调研，第 2–4 步 skipped。不能转为“只下载不运行”继续。
- 第 2 步目标歧义、第 3 步账号登录/切换节点等可以 waiting_user。等待只阻塞依赖该输入的分支，不代表用户同意。
- 第 3 步某渠道失败后继续下一个未尝试渠道。搜索批次用尽且仍需寻找新来源时，按 [回路预算](loop-budget.md) 等待用户决策。
- 第 4 步校验失败可回到第 3 步的下一条未尝试路径。保留尝试记录和搜索轮数，不混包修补或重置循环额度。
- 每个退出路径都报告结论及恢复结果；环境检查失败时没有修改网络状态，只需说明原因和最小修复动作。

## 正文进度协议

开始时先给出当前阶段和接下来的动作；每个阶段切换、重要检测结果、用户等待、渠道降级和最终状态都用聊天正文更新。无需每次重贴整张表，不用不可验证的进度百分比。

正常执行示例（内容仅为格式示例，实际设备/结果必须来自工具）：

```text
【1/4 环境检查｜进行中】检查 SDK、真机、模拟器和 VPN。
【1/4 环境检查｜完成】发现 1 台已授权设备；另有 1 个配置完整但未启动的 AVD。VPN 已盘点，出口地区尚未核实。
【2/4 目标识别与信息补齐｜进行中】根据商店与官网查询包名、开发者和可用版本。
【2/4 目标识别与信息补齐｜完成】已定位唯一目标，无需用户补充信息。
【3/4 获取安装包｜进行中】依次检查本地样本、设备导出、官方与镜像渠道。
【3/4 获取安装包 · 搜索兜底 1/3｜进行中】已知渠道均无合适样本，搜索新的镜像来源并排除已尝试项。
【3/4 获取安装包 · 搜索兜底 2/3｜进行中】上一轮候选均失败，本轮发现 2 个新增来源，继续实际取包。
【3/4 获取安装包｜完成】4 个分包已完整保存，尚待身份与签名校验。
【4/4 校验归档｜完成】包名、版本、必需分包与签名检查通过，文件和来源记录已归档。
【收尾｜完成】本次临时网络变更已恢复。
```

缺设备时：

```text
【1/4 环境检查｜失败】NO_ANDROID_DEVICE：没有已授权且可响应的设备，也没有配置/系统镜像完整的 AVD。已中断调研。
【2–4/4 调研执行｜跳过】环境门槛未通过，没有查询渠道或下载安装包。
【收尾｜完成】请连接并授权真机，或先准备完整 AVD；完成后重新执行环境检查。
```

长步骤至少每 60 秒内提供一次事实更新，工具等待应分段返回。工具内部进度只是证据来源，不能替代 agent 在正文向用户说明。等待用户时正文显示等待原因，问题本身使用当前可用的用户输入工具提出；恢复后核查新状态。

## 1. 环境检查

先执行 `python3 scripts/preflight.py --report <任务目录>/environment.json`，再进行任何商店、镜像、包名搜索。国家已知时可追加 `--country`；未知无需先打断用户询问，先完成不依赖国家的设备检测。脚本优先用 `CLI run` 执行（见 [CLI 执行](cli.md)）；这里的 `python3` 是参数简写，直接执行时必须先切到 `$RESOURCE_ROOT`。

通过需同时满足：返回码 0、报告 `status=passed`、`downstream_allowed=true`。退出码 4 表示硬门槛失败。真机/在线模拟器要求 ADB 授权且 shell 可响应；未启动 AVD 要求 emulator 程序、配置以及 system/ramdisk/kernel 镜像存在。配置完整不等于已验证启动，使用前仍需启动并核实运行状态。

设备缺失时立即报错中断，不自动安装 SDK/新建模拟器，不先要求登录/VPN/验证码。未授权设备提供批准 USB 调试的修复说明；环境修好后从本阶段重跑。第 1 步不会切换 VPN 或启动 AVD。

## 2. 目标识别与信息补齐

从链接、现有 APK、历史归档解析：App 名称、目标国家/地区、Android 包名、期望版本、输出位置。用户未指定输出位置时，使用当前工作区内 `app-research/<package>/<version-or-attempt>/`；跟随已有归档规范，目录用英文包名。不要写回 skill 目录。

用户只需提供足以定位的线索，例如名称+国家、商店链接或已有 APK。由 agent 查询和解析其余信息，不要求用户填写完整表单：

| 信息 | 自动补齐来源 | 需要用户输入的情况 |
|---|---|---|
| 名称/链接 | 用户请求与上下文 | 完全没有目标线索 |
| 市场 | 请求上下文、官网与发行信息交叉核对 | 多国同品牌包且无法唯一确定 |
| 包名 | Play URL 的 id、官网商店链接、APK Manifest、按名称搜索 | 多个可信候选无法排除 |
| 开发者 | 商店、官网和已有样本，用于交叉核对 | 通常不问 |
| 版本要求 | 用户明确要求；否则自动查询渠道返回的较新版本 | 指定版本取不到、需要降低版本标准时 |
| 保存位置 | 当前工作区既有归档规则或默认目录 | 无工作区，或存在无法判定的多个归档位置 |

- 有完整 Google Play 链接时优先采用其包名；用开发者、官网和目标市场交叉核对。商店 `hl/gl` 是查询参数，不保证应用发行市场或账号地区。
- 同名或同品牌多国包存在歧义时，先展示候选包及依据，让用户选择；等待期间可查询候选元数据。不能把另一个国家的包当作成功。
- 指定版本必须满足。未指定时优先取可核实的较新版本；只有商店/API 明确给出查询时间和可用版本时才声称“该渠道当前返回版本”，不要直接声称全渠道最新版。
- 此模块只处理 Android。用户实际要 iOS 时说明本 skill 不适用并停止，不能以 Android 样本代替 IPA。

任务目录确定后先初始化校验账本，纯下载同样执行；`review.json` 可以稍后创建：

```sh
mkdir -p "$TASK_DIR"
python3 "$RESOURCE_ROOT/scripts/check_delivery.py" init "$TASK_DIR/review.json"
```

取包账本是另一个文件，在第 3 步用 `attempts.py init` 单独建立，两者不要混用。

## 3. 获取安装包：有顺序的子工作流

“就绪”表示所需权限、会话、设备、地区网络和工具已具备。无需为进入一个渠道提前要求用户完成所有登录和配置。

完整调研/UED 在设备相关取包前确定预期运行设备及其 ABI、SDK、密度；原包导出的取包设备可不同，分别记录。对会按设备条件返回分包的渠道，在尝试开始时用 `--profile` 记录实际采用的条件（字段仅 `abi`、`sdk_level`、`density`，后两者为正整数），并传给对应取包工具。纯下载按用户目标或渠道实际条件记录，不要求额外运行 App。不要用历史默认 profile 代替检测结果。

指定 versionCode 时，所有 `download.py` 渠道及 `export_device.py` 均传 `--version-code`；它会保存为 `download.json.requested_version_code`，供第 4 步自动承接。`source_version_code` 仅是渠道返回值，不能当作用户要求；匿名 Play 未指定版本时仍先通过 getItems 查询。

| 顺序 | 路径 | 执行与降级条件 |
|---|---|---|
| 前置 | 主流程环境与目标确认 | 必须已经通过第 1 步设备硬门槛和第 2 步身份确认；再查指定工作区/已知归档，不扫描无关个人文件 |
| 1 | 已有本地样本 | 检查版本、来源、哈希、分包；满足要求则复用，不重新下载；不够新则继续 |
| 2 | 已连接设备已安装 | 按 [设备选择顺序](network-and-devices.md#设备选择顺序) 选择取包设备，只读检查 `pm path` 并导出所有 APK。设备没有安装则不要求用户先去安装 |
| 3 | 开发者官方直接分发 | 官网真实 APK 链接可以直接取；仅跳 Google Play 则转下一步，不把官网宣传页当下载源 |
| 4 | 已就绪模拟器 Google Play | 免费目标 App 可直接安装并导出；要登录/切网络/新建模拟器时转入用户介入分支，先继续低交互路径 |
| 5 | 匿名 Google Play | 先复用有效 profile 和已注册 device ID；未指定版本时执行 getItems 自动查询 versionCode，再执行 delivery 和全部文件下载。缺输入先检查已有工具并按需注册；不得因为不知道版本号或账号接口失败就跳过匿名渠道 |
| 6 | Aptoide API | 下载主包与完整分包；普通网页失败不代表设备 profile 的 AAB API 也失败 |
| 7 | APKPure API | 查询客户端 API 的 APK/XAPK 地址；保留原始归档并核对实际版本 |
| 8 | APKCube 浏览器下载 | 选择正确包名与版本，等待生成；验证码由用户处理。人工阻塞期间继续独立渠道 |
| 9 | 其他相关已知镜像 | APKCombo、APKMirror、PGYER、LDPlayer 等按当前包的已知条目依次尝试；每个来源记录结果，重复项直接排除 |
| 10 | Web Search 兜底，每批最多 3 轮 | 每轮“自主搜索新来源 → 全量去重 → 实际尝试新增候选”。成功提前结束，批次耗尽后由用户决定是否继续 |

用户明确指定渠道/优先级时遵从其要求，其余按表中顺序。每条路径在取包阶段即时处理依赖和必要确认，未就绪则记录原因后尝试下一条；用户回复后可继续原等待项。取得目标样本就进入第 4 步校验，无需为了走完列表继续下载。旧样本只作保底，不能取消指定版本任务。

### 任务级尝试记录与去重

第 3 步开始，在本任务目标目录创建 `attempts.json`，按包名与版本要求隔离。记录必须覆盖本地/设备、已知 API/镜像和后续搜索新增来源。继续同一任务必须读取原记录，禁止换目录后重置历史。

- 每次访问实际取包入口之前登记 begin；完成后 finish，记录方法、来源、状态、失败原因、候选 URL、真实重定向来源及产物/校验记录。
- 已知子流程按“来源 + 方法”排重。例如 Google Play 的已登录模拟器与匿名 delivery 是不同已知方法；同一方法已经试过就不从头重试。传输层有界重试属于同一次尝试。
- 元数据刷新/短效链接重取也属于尚未结束的同一尝试，可使用新的传输目录但保留同一 ledger id；所有该次允许的重试用尽才 finish 为 failed。不能先把它终结为 failed，再新建方法名称绕过去重。
- Web Search 兜底按**整个已尝试来源**排重，不只比较 URL。排除网页/API/下载域名别名、移动版/语言版以及已记录的重定向目标。换了页面路径或临时签名不算新来源。
- 新站若最终跳回已经试过的平台，只记录重定向并排除，不再次执行同一个平台下载。不同域名最后得到同一文件时按来源记录和 SHA-256 识别，已失败或不满足要求的文件不能再算新候选。
- `waiting_user`、`dependency_missing` 和 `verification_failed` 也进入排除集合；只有用户补齐原等待条件时才继续原尝试，不把它当新搜索来源。
- **有证据的 profile 变化例外**：若第 6 步发现需要不同 ABI/SDK/密度，保留原记录，用相同来源/方法、新 `--profile`、原 `--parent-id` 和 `--reason` 建立关联尝试。父尝试须已结束且已有 profile；新 profile 必须不同且未试过。该操作只继续原来源，不领取/重开搜索轮次，也不能当作新搜索来源；等待中的尝试仍按原 id 续办。
- 新候选若只是信息页/商店跳转/PC 安装器，记录实际结果后排除；后续各轮不再访问同一来源取包。

使用 `scripts/attempts.py` 管理记录；完整参数运行 `--help`：

```sh
python3 scripts/attempts.py init --ledger /absolute/target/attempts.json --package com.example.app --version-policy latest-available
python3 scripts/attempts.py begin --ledger /absolute/target/attempts.json --channel aptoide --method app-get-aab --url 'https://ws75.aptoide.com/api/7/app/get'
python3 scripts/attempts.py finish --ledger /absolute/target/attempts.json --id 1 --status failed --reason 'no matching package'
```

上例的目录和包名是占位，执行时替换。begin 输出的实际 id 用于 finish；本地/设备路径可只传 channel，无需假造 URL。来源 URL 使用公开页面/入口，不写入 Cookie、token 或签名下载链接。

设备相关的首次 `begin` 追加 `--profile /absolute/acquisition-profile.json`。该文件的结构示例为 `{"abi":"arm64-v8a","sdk_level":35,"density":480}`，数值须替换为实际取包条件。切换后的新文件同理；关联取包示例（id、路径与理由替换为实际证据）：

```sh
python3 scripts/attempts.py begin --ledger /absolute/target/attempts.json --channel aptoide --method app-get-aab --url 'https://ws75.aptoide.com/api/7/app/get' --profile /absolute/new-profile.json --parent-id 1 --reason '已核对所选运行设备的 ABI 与原取包条件不同，证据见本任务设备记录'
```

关联尝试不传 `--search-round`；即使三轮已耗尽也可继续原来源的有据 profile 变更，旧尝试保持原状态。同来源/方法的相同 profile 仍拒绝，不能靠不断填写不同理由重复。

### Web Search 三轮循环

搜索由 agent 调用实际可用的 Web Search 工具完成，脚本只管理计数和排除集合，不代替搜索：

1. 已知路径均已尝试或明确记录未就绪后，读取 attempts summary。按完整包名、原生语言名称、市场及 APK/APKS/XAPK 等关键词自主生成本轮查询；可加入已试来源的 `-site:` 条件，但结果仍必须经完整记录过滤。
2. 调用 `attempts.py search-round --ledger ... --query '<实际查询>'` 领取当前批次的轮次，记录本轮查询。每轮可重复传多个 `--query`，只执行脚本返回的非重复 queries。每批第 4 次领取会被拒绝。领取后实际调用 Web Search 并观察结果。
3. 对搜索发现的每个相关候选，先调用 `candidate --ledger ... --url '<实际来源页>'`，`eligible=false` 就直接排除，不打开取包页面。未尝试候选通过 begin（`--search-round N`）登记，再实际核对包名/版本、尝试下载或交用户完成必要验证。开始搜索后新来源必须标当前已领取轮次；不能省略轮次或重开旧轮。已等待用户的原尝试可在条件补齐后按原 id 继续。
4. 本轮所有相关新增候选失败，或根本没有新增候选，都消耗这一轮；总结正文后继续下一轮。下一轮查询应根据失败结果调整，例如完整包名查找、原生名称/开发者查找、指定版本/历史镜像查找，不能重放原查询和原来源。
5. 下载到符合目标的样本就提前进入第 4 步校验；校验失败将该尝试记为 verification_failed，再从剩余未尝试候选继续。轮数和排除集合不重置。
6. 当前批次完成后暂停新增来源搜索，核对已知路径及依赖补齐项；仍有未执行的匿名 getItems/delivery、可修正协议或已就绪依赖时继续原尝试。仍需继续搜索且有新角度时，按 [回路预算](loop-budget.md) 询问用户。缺搜索工具属于 `search_unavailable`，记录实际情况。

用户明确同意再搜索一批后，在同一个 ledger 上执行 `attempts.py resume-search --ledger ... --after-round N --reason '<用户决策和新的搜索方向>'`。N 使用 summary 的 `search_rounds_used`。此命令只续开已耗尽的当前批次，使 `search_rounds_remaining` 恢复到 3；累计轮号、旧查询及来源排除集合保留。下一次耗尽后再次询问。

搜索只发现结果而没有实际取包，不算某来源下载成功。正文每轮至少报告轮次、发现候选数、排除数、新增尝试结果；例如 `【3/4 获取安装包 · 搜索兜底 2/3｜进行中】发现 5 个候选，排除 3 个已试来源，尝试剩余 2 个。`

若子流程中的“已就绪模拟器 Google Play / 匿名 Google Play”依赖未就绪，在 Aptoide/APKPure 查询完成后给用户一个具体选择：例如“镜像只有旧版；已有完整 AVD，但需要你登录目标地区 Play。是否打开该模拟器继续？”用户不愿登录则继续浏览器镜像与已有设备路径；这只适用于主流程第 1 步已经通过的环境。

## 4. 校验归档

先读 [校验与交付](verification.md)，再运行 `scripts/verify.py`。样本目录自动读取其 `download.json.requested_version_code`；传 `apks/` 子目录或单文件/归档时，只有相邻取包记录实际列出该目录内 APK 或该产物，才承接记录。没有关联记录的本地/手工样本，指定版本时必须显式传 `--version-code`。显式参数和记录不一致直接失败，不能用参数覆盖原要求。

核对返回码和 `verification.json` 中的目标/实际版本、来源文件集、工具证据及未完成项。返回 0 只代表已执行的文件检查通过，不能替代官方来源、运行资源与安装适配判断。身份/签名失败回剩余渠道；profile 变化按关联取包处理；只下载任务完成本步和收尾后交付。

## 授权范围与确需用户提供的输入

完整调研中的例行同意、测试权限、启动/安装、调试和隔离 Mock 按 SKILL.md 的连续执行规则处理。本表的等待只针对不能从已有授权与环境解决的输入，不将每个系统弹窗都升级为确认。

| 情况 | 自动完成的准备 | 用户需要做什么 | 后续动作 |
|---|---|---|---|
| 名称对应多个市场/包 | 查候选、开发者、官网 | 选择市场或包名 | 按选定包继续 |
| 多台可用设备，差异影响取包 | 只读查看目标包是否已装、版本/ABI | 只有无法依请求确定目标时，选择具体设备；已有指定则不问 | 所有 adb 命令带 `-s SERIAL` |
| 只有 `unauthorized`/offline 设备且无完整 AVD | 第 1 步失败并中断，说明具体状态 | 解锁/批准 USB 调试或恢复设备连接后告知重试 | 从环境检查重新开始，不在本次继续取包 |
| 无设备且无完整 AVD | 第 1 步失败并中断，输出最小修复动作 | 用户另行连接真机或准备模拟器环境；设置环境是独立授权任务 | 修好后重跑第 1 步，不在下载流程内自动装模拟器 |
| 目标国家 VPN 节点存在 | 读取当前组、节点、候选与代理模式，准备恢复值 | 确认切换到具体节点及影响范围；若已明确授权该切换则继续 | 切换、核验出口/连通、完成后恢复 |
| 没有目标地区节点 | 查已有订阅节点，说明当前限制 | 可选提供节点、目标地区网络或选用设备/镜像路径 | 不自行购买订阅或导入不明配置 |
| Google Play 未登录 | 打开所选模拟器官方商店登录页 | 手动登录和完成二次验证 | 只检查登录是否完成；不索要密码或恢复码 |
| 免费应用安装到任务专用模拟器 | 已选设备、核对包名/免费状态 | 下载任务通常已包含此必要安装，无需再问一次 | 安装后导出完整分包 |
| 要在个人/共享真机新安装、升级或覆盖 App | 展示包名、版本、设备及已有版本 | 明确同意该安装/更新；仅导出不需要这个确认 | 按批准范围操作，不卸载原应用 |
| 调研专用环境中的常规首次隐私/用途/一般服务说明 | 确认属于当前调研 App，保留页面与操作证据 | 完整调研授权内直接推进，不逐次确认；已有明确授权不重复询问 | 涉及真实金融交易或个人敏感资料提交则改走隔离 Mock |
| APKCube/其他网站人机验证 | 导航到确切验证页面，保留状态 | 手动完成验证 | 核查磁盘文件，不以“下载开始”页面作为成功 |
| 需要付费 App、购买账号或订阅 | 展示确切项目和费用 | 用户决定购买或改走已有授权设备 | 不自行付费 |
| 仅有旧版本/来源无法独立核验 | 下载并标明实际证据、继续找目标版本 | 若要用较低标准作为最终交付，用户决定是否接受 | 标注已接受的限制，不修改原需求 |

同一会话已有授权不重复确认；授权须覆盖具体动作。例如“必要时使用鹿语云菲律宾节点”已授权该切换，“匿名下载”本身没有授权改变全局 VPN。将与当前阻塞有关的问题一次合并，避免登录、VPN、设备选择分别反复打断。

## 重试与结束

- 传输层对超时、429、5xx 最多 3 次有界重试。403/404/410/地区受限不原样重复请求。
- APKPure 签名直链失效时重新查询一次元数据，按新文件身份重新下载；禁止把不同版本的 `.part` 拼接起来。
- 匿名 Play 遇到 `DF-DFERH-01`、`AppNotPurchasedError` 或 delivery denied，区分条款、账号/地区、设备注册和协议问题；只在有新证据时调整一次。现有 apkeep 失败不代表 Aurora 当前匿名协议也失败；不要把“有应用详情”当作“能取包”。
- APKCube `FETCHING` 可短时轮询，单次等待不超过 30 秒、总计约 2 分钟；仍未就绪则记录状态并换源，不无限等待。用户要继续等时按其要求执行。
- 下载成功后立刻校验。如果只是“下载”任务，校验后可结束；若用户还要求可运行，继续选设备并执行安装/启动验证。
- 搜索兜底每批最多 3 轮。批次用尽后等待用户决策。已知路径的有据纠错或依赖补齐仍可按对应额度推进；重新校验、继续会话或切换镜像目录沿用原计数。
- 所有可行路径均受阻时列明：已取得什么、缺什么、每条失败原因、下一项最小用户动作。用户交互未完成时不得把任务标为成功。
