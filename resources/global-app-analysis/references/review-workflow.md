# 第 9 步证据审查工作流

业务调研和 UED 共用本流程。第 5 步用[审查清单](review-checklist.md)设计覆盖，第 8 步形成草稿和运行记录后进入 9.1。纯下载在第 4 步完成 APK 校验后交付。

## 9.1 准备证据并清点缺口

从原范围、场景、页面和证据清单为每个适用面列出应审项 ID，并写明本轮要读的文件。审查者必须用文件读取工具从磁盘打开这些文件，不能依据上下文或上一轮摘要；各项粒度应足以判断对应问题、分支或页面的证据是否齐全。

先查草稿、流程图注释、清单和运行记录中标记为未查、未测、未走通、未用模拟数据、待确认、未知或含义相近的项，再检查未标记但缺少代码或运行证据的项。按问题、路由、页面或分支 ID 登记缺口及下一项确认动作。已有完整实测时可引用证据关闭“未用模拟数据”项。其余优先补证，可并行核查独立审查项。

## 9.2 分工并收齐本轮结果

按[审查清单](review-checklist.md)分派本轮适用审查面。能隔离时每面开新审查上下文；使用当前客户端提供的子 agent / 隔离审查能力（例如 Codex 的 `spawn_agent` 可设 `fork_turns: "none"`，其他客户端用等价工具）。先给原始问题、范围、原始证据入口和分工，让审查者独立枚举，再给草稿、已知缺口和现有清单做比对。名额不足时依次启动。无法隔离时，主 agent 在当前会话分面执行相同的枚举与比对，并记录执行方式。

每面按开审清单逐项回传结论、证据位置和判断依据，未解决的项关联缺口 ID。审查者核对每条拟判不可执行路径的必要前置条件、检查结果及原始证据。证据不足时记录为待补证并回 9.3。全部适用面交齐逐项结果后才进入 9.3 或复审；审查者结果不全时补齐该面，必要时使用当前会话复核。多个审查者并行只算一轮。分歧回查原证据，共用设备上的实测由主 agent 排队协调。

## 9.3 修正、补证或判定阻塞

按[完成条件](completion.md)分派缺口，合并同轮问题并按[回路预算](loop-budget.md)计数。缺实现或入口证据回第 5–6 步，缺交互或图片回第 7–8 步，图文矛盾同步修正。必要场景在 App 宿主执行，按[运行与 Mock](runtime-and-mock.md)处理登录、会话和数据条件。回填原清单，保留本轮审查记录；修正完成后回 9.1 重新审查，不能直接进入 9.5。需要外部输入或续批时按[阻塞判定](completion.md#真实阻塞与结论边界)记录并保留恢复点。

## 9.4 对当前文件重审

首审结束后至少独立再审一轮，即使首审没有发现。审查必须重新打开磁盘上的当前文件，按文件实际内容判断；修改事实、范围、流程图或验收证据后，重新读取同一文件并从 9.1 重开一轮，不能只重跑 10.4。按完整范围重新审定当前文件的全部应审项，保留未受修正影响的应审项 ID，并逐项记录原证据为何仍适用或引用新证据。阶段性结论也保留所有应审项及缺口。补测及主 agent 修正自检作为复审输入。复审中新发现问题回 9.3，直到最后一次修改后的文件通过。

## 9.5 检查第 10 步入口

放行前逐字回答下面三问，任一为“否”就回 9.1，不要先交付再补审：

1. 最后一轮修改之后，是否还有一次独立审查？（改错别字、换图、调链接都算修改）
2. 那次审查读的是当前这份文件，而不是上一版？自读、自动检查、截图或 grep 都不能代替。
3. 那次审查提出的每条“需修正”是否都已处理，并写清处理结果？

轮次按“一次针对同一版本的分工审查”计；并行发出的多名审查者算同一轮，修改后再审另计一轮。

核对[完成条件](completion.md#第-9-步的完成门槛)，确认首审和独立复审覆盖当前文件的全部应审项、缺口已关闭或按阻塞规则记录。审查通过后才能生成报告/图册；10.4/album 通过不是完成信号，交付前还要重新打开实际文件确认。真实阻塞或用户要求先看时，只对已核实范围审查并交付，剩余缺口保持开放。通过后进入[报告审查](report-review-workflow.md)或 [UED 图册验收](ued-workflow.md#交付验收与进度)。
