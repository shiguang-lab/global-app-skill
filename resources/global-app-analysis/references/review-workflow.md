# 第 9 步证据审查工作流

业务调研和 UED 共用本流程。第 5 步用[审查清单](review-checklist.md)设计覆盖，第 8 步形成草稿和运行记录后进入 9.1。纯下载在第 4 步完成 APK 校验后交付。

## 9.1 准备证据并清点缺口

记录轮次、原始用户问题、App/版本、范围、实际加载资源及草稿版本。定位现有页面/状态/分支清单、原代码、运行日志、fixture、图片和草稿，选出本次适用的审查项。沿用已有复核记录，没有时使用任务目录的 `review.md`。

先逐项检查草稿、流程图注释、清单和运行记录中的“未检查、未分析、未走通、未用模拟数据走流程、未测试、待确定、未确认、未找到、未知、可能”等表述及同义标记，也查缺代码依据、实际操作或运行结果的条目。将每个范围内缺口关联到问题、路由、页面或分支 ID，写清下一项确认动作，优先补证。其他审查项可同时推进。必要场景已有完整实测时，引用运行证据即可关闭“未用模拟数据”项。

## 9.2 分工执行审查

1. 根据[审查清单](review-checklist.md)分配适用的审查面。业务调研分给业务与状态码、页面与图片两个审查者，有 H5 时另开 H5 审查者。纯 UED 分配页面与图片审查，有 H5 时另开 H5 审查者。混合目标共用相同范围和证据，审查者可核对交界处。
2. 执行环境支持时，每个审查面开一个**新上下文**的子 agent 或审查会话。支持 `spawn_agent` 时，每个分工调用一次并设 `fork_turns: "none"`。初始消息给原始用户问题、范围与版本、工作目录、证据入口、负责的审查项，以及下文要求的返回字段。先只提供原始证据入口，审查者提交独立枚举结果后，再给现有清单、草稿和已知缺口做比对。复审使用新上下文，优先由未参与对应分析或修正的审查者执行。并发名额不足时按分工依次启动，无法隔离时主 agent 按相同顺序分项复核并记录实际方式。
3. 审查者并行只读检查，交回关联 ID、版本、触发条件、证据位置、实际结果或缺失证据，以及「通过／待证实／需修正／有证据的不适用／真实阻塞」和下一动作。主 agent 汇总差异，分歧以回查或实测解决。需要共享设备、会话或 Mock 的复现由主 agent 排队协调，隔离环境可并行。

## 9.3 发现问题时继续分析

将 9.1 和 9.2 发现的未关闭项写回原清单，保留发现、修正与验证记录。合并本轮缺口，先按[回路预算](loop-budget.md)检查并记录证据返工轮次。缺资源、入口或原实现依据时回第 5–6 步，缺状态、交互或截图时回第 7–8 步，图文和证据不一致时修正对应草稿。必要场景缺实测时，在 App 中从原入口执行。现有数据无法触发时，用隔离 fixture 从原数据输入层驱动原组件，记录实际操作、请求与响应、页面变化和结果。回填新增证据并更新受影响的图文，复审通过后关闭缺口。真实阻塞按[完成条件](completion.md#真实阻塞与结论边界)处理。

## 9.4 从 9.1 重新审查

首审结束后至少再审一轮。补证、重跑和更新草稿后，**从 9.1 重新进入审查**，以更新后的版本和证据重新检查所有适用的审查面。复审必须逐条核对上轮缺口的关闭依据、修正影响的上下游和覆盖范围，核对同版本已有证据是否仍适用。首审无发现时，第二轮仍独立回查待查项的关闭依据和关键原始证据。复审发现新问题时回 9.3 检查额度，再补证或等待用户决策。

## 9.5 判定能否交付

按[完成门槛](completion.md#第-9-步的完成门槛)记录适用的业务事实、实际交互和页面图片结论。完成首审及复审、范围内待证实与需修正项均已关闭，才进入第 10 步正式交付。真实阻塞或用户要求先看时，可交付已核实部分，并在聊天和内部记录缺口与恢复动作。

第 10 步按[报告审查工作流](report-review-workflow.md)或 [UED 图册验收](ued-workflow.md#交付验收与进度)检查实际交付物。业务条件、连线、结果、页面状态或 H5 范围变化时从 9.1 重新审查。
